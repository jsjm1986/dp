对本仓库执行一轮完整的代码质量审查，标准与流程如下。$ARGUMENTS 可选，为额外关注点（如"重点看支付"）。

## 1. 全量通读（不允许抽样、不允许幻觉）

- 用 `git ls-files` 生成完整文件清单，逐个阅读全部业务源码、配置、schema、脚本与文档；
- 生成物（`src/generated/**`、lock 文件、构建产物、静态资源）可结构化抽样，但必须在报告中声明口径；
- 建立阅读台账，报告末尾附覆盖率表，未读到的内容明确标注"未读"。

## 2. 多维度审查（每个维度都要给结论与证据）

- **安全**：逐路由核对鉴权守卫；资源归属校验；上传/注入/XSS 面；密钥与生产门控；
- **资金正确性**：所有涉及余额/退款/提现/佣金的路径是否事务内、条件更新防并发、带流水；
- **并发与一致性**：check-then-act 竞态、唯一约束兜底、幂等性；
- **状态机**：订单等状态的转移矩阵是否闭合、非法转移是否被拒；
- **性能与扩展**：N+1、分页、进程内状态、规模天花板；
- **代码质量/可读性/可维护性**：分层一致性、重复代码、死代码、`any`、命名、注释质量；
- **测试**：单测/e2e/冒烟的真实覆盖，找出"假绿"用例；
- **文档与仓库卫生**：文档漂移、误提交的产物、README 准确性。

## 3. 运行验证（不以肉眼为准）

- `server`：`pnpm lint`、`pnpm test`、`pnpm test:e2e`、`pnpm build`；
- `web`：`pnpm build`（含 vue-tsc 类型检查）；
- 起服务跑 `python3 scripts/smoke.py`，全部通过才算基线；
- 所有结论性问题（如"构建失败""测试假绿"）必须实际复现取证。

## 4. 产出

- 将审查结论写入/更新 `docs/CODE_REVIEW.md`：总体评价、按 P0–P3 分级的问题清单（带 file:line）、各维度专项、已修复项、路线图；
- 只修"客观错误且改动安全"的问题（构建失败、lint、口径错误、缺事务等），修复后必须全量回归；
- 设计层/产品层问题只记录不改码，避免扩大回归面。

## 5. 交付（PR 流程）

- 新建分支（如 `review/yyyymmdd`）提交：报告 + 安全修复 + 命令/文档更新；
- 推送并创建 PR；无 remote 时在本地以 `--no-ff` 合并回 main，并向用户说明差异；
- 合并前确认：lint 0 警告、双端 build 通过、测试与冒烟全绿。
